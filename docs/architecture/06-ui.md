# Architecture 6 — `ui`: the UI toolkit

[← docs index](../README.md) · prev: [Cache, session, i18n](05-services.md) · next: [ECS engine](07-ecs.md)

`ui` is the component toolkit and the home of the performance laws — no pop-in, no
blocking, the 14KB rule, and deferred sections. There is **one kit**:
`ui/driftwood`, a package of exported templ components called directly.

## Views are templ; the kit is a package

Every view — framework, kit, and example app alike — is a `.templ` component
compiled by `templ generate` (templ is a Go tool: `go tool templ generate`, run by
the root Makefile's `gen` target; the generated `*_templ.go` files are committed so
plain `go build` works without running gen). The local templ reference is
[docs/templ.md](../templ.md).

There is no Kit interface, registry, or context injection. A component is a
package-level templ function you call by name — `@driftwood.Card(p) { ... }` — with
immutable props structs (living in `driftwood`) carrying typed `datastar.Attrs`.
A wrong call is a compile error, not a registry miss. The framework's own error
rendering goes through `driftwood.ErrorPage`/`driftwood.ErrorAlert` (`render.go`).
`ui` itself keeps just two primitives, both `.templ`: `ui.Icon` and `ui.Defer`.

`ui.Icon("gear", ui.IconSize(...), ui.IconLabel(...))` emits
`<i class="icon icon-gear">`; the glyphs render through a Unicode `::before` map in
`input.css` — a deliberate stand-in until the planned build-time-subset icon font
ships (the font would contain only the glyphs the code references; `ui.UsedIcons()`
already tracks them).

## Tokens

Color and type come from **Tailwind v4 + `rybitten`** — one generated `app.css`,
built from `pkg/beach/view/css/input.css` (`make css`) and served by the framework.
The kit emits semantic `dw-*` classes; the sheet styles them via `@apply`, so markup
stays clean and the whole kit restyles from one place. `input.css` defines the whole
token vocabulary, dark-first:

| Group | Tokens |
| --- | --- |
| Surfaces | `--color-paper` (page) · `--color-panel` (cards/chrome) · `--color-panel-hover` |
| Ink | `--color-fg-default` · `--color-fg-muted` |
| Edges | `--color-line-soft` · `--color-line-strong` |
| Accent | `--color-accent` + `-hover`/`-text`/`-soft` (a munsell teal) |
| Roles | `--color-good` / `--color-warn` / `--color-bad` / `--color-info` |
| Series | `--color-series-a…o` (15) — generated from the RYBitten munsell gamut via `rybitten.SeriesVars` ([rybitten](19-rybitten.md)); eight alternate `[data-chart-theme]` palettes plus munsell redefine them per scope |
| Type | `--font-sans` / `--font-mono` (system-first stacks) |

The Tailwind `@theme` block pins the `--radius-*` scale to `0px` — the sharp-corner
house law — so no component can round a corner without changing the law itself.

Dark is the default theme — `.dw-root { color-scheme: dark }` — with the server
rendering final color before paint (no flash). House rule: the kit writes semantic
CSS (clean markup, styling lives in the sheet), and `beach-vet` flags any hardcoded
hex/OKLCH in templ or kit CSS — color goes through a token. Type uses a system-first
stack so no font is fetched from a CDN; vendoring a specific webface (local
`@font-face` from `/static/fonts`) is a per-app opt-in.

The concrete inventory — every component, tiered by which example app proves it,
plus the **specimen** page (`ui/specimen`) that renders them all — is
[16-components.md](16-components.md). This doc is the mechanism; that one is the parts list.

## The performance laws

These are toolkit contracts, not advice. Every kit component and every skeleton
template is built to satisfy them, and the example apps' perf gate measures them.

### No pop-in

The first paint is the final paint — for everything in the response. The server
renders final state, including signal initial values from cookies/session/DB; hidden
things ship hidden; no visible HTML is ever generated in client JS; theme classes
are on `<html>` before paint. Deferred sections (below) do not violate this law
because they reserve their exact dimensions up front: late content fills reserved
space, it never moves rendered pixels.

### No blocking

Nothing blocks first paint or the main thread. The stylesheet is the only
render-blocking resource, and it's immutable-cached so it costs one fetch per
deploy. Fonts are system-stack (no fetch at all); a vendored webface would use
`font-display: swap`. JS ships as deferred ES modules (`datastar.js` +
`chart.js`), so parsing never blocks rendering and a page is fully usable —
every CSS-native component works — before any script executes. SSE connects
after load; no synchronous XHR, no third-party scripts, no external CDNs.

### HTML and CSS first

Two scripts ship in the driftwood page head, both deferred modules: **Datastar**,
which earns its place only for what the platform genuinely can't do without script —
talking to the server (`@get`/`@post` fragments), signals shared across elements,
SSE patches — and **`chart.js`**, the chart interaction layer (tooltips, crosshairs,
the widget toolbar — [14-analytics.md](14-analytics.md#the-client-interaction-layer)),
which is pure progressive enhancement over server-rendered SVG: every chart renders
and updates without it. Everything else is HTML and CSS.

The platform does far more than it gets credit for: disclosure and accordions are
`<details>`/`<summary>`; modals are `<dialog>`; popovers, flyouts, and tooltips are the
`popover` attribute plus CSS anchor positioning; tabs, toggles, and menus open with
`:checked`/`:target`/`:focus-within` and native form controls. The kit builds every one
of these with **zero script**, so they work before any bundle loads, survive a script
error, and cost nothing on the main thread. Local presentational state — open/closed,
which tab, hovered — is never JavaScript. A component that reaches for script to do what
CSS already does is a defect.

This is what makes [no blocking](#no-blocking) hold so easily: most of a page is fully
interactive with no JS at all, and Datastar's bundle matters only the moment the user
does something that needs the server.

### The 14KB rule

A fresh TCP connection's initial congestion window is ~10 segments ≈ 14KB: a first
response that fits arrives in **one round trip**, before slow-start ever matters.
So `View.Page` targets **≤14KB compressed** — shell plus above-the-fold content,
server-rendered, complete. Everything heavier becomes a deferred section.

Enforcement is measurement, not vibes: in dev mode the framework logs every page
response's compressed size and warns over budget; the example apps' perf history
(JSONL, tracked in git) gates the budget in CI. The stylesheet doesn't count against
the 14KB (it's a separate cached request) — the budget is the HTML document.

### Deferred sections

Anything bigger than the budget lazy-loads over Datastar. `ui.Defer` renders a
server-side placeholder with **exact reserved dimensions** (kit-styled skeleton,
zero layout shift) and a Datastar `@get` that fires on viewport intersection (or
load, for behind-a-tab content):

```templ
@ui.Defer(ui.DeferProps{
    ID:     "trade-history",
    Height: "24rem",                  // reserved space — late fill, no shift
    Get:    "/wallet/history",        // lands on a PageFunc; fragment patches in
})
```

The `@get` hits a normal `beach.PageFunc` — the framework's dual-purpose branch
returns the fragment, the patch morphs into the placeholder. Deferred sections live
below the fold or behind interaction; above-the-fold content is always in the first
response. One mechanism, three uses: 14KB overflow, expensive queries that shouldn't
block the first paint of cheap content, and behind-interaction panels.

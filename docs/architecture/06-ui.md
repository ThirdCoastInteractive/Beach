# Architecture 6 — `ui`: the UI toolkit

[← docs index](../README.md) · prev: [Cache, session, i18n](05-services.md) · next: [ECS engine](07-ecs.md)

`ui` is the component toolkit and the home of the house laws — no pop-in, no
blocking, the 14KB rule, deferred sections, and accessible by construction. There is
**one kit**:
`ui/driftwood`, a package of exported templ components called directly.

## Views are templ; the kit is a package

Every view — framework, kit, and example app alike — is a `.templ` component
compiled by `templ generate` (templ is a Go tool: `go tool templ generate`, run by
the root Makefile's `gen` target; the generated `*_templ.go` files are committed so
plain `go build` works without running gen). templ's own docs: [templ.guide](https://templ.guide).

There is no Kit interface, registry, or context injection. A component is a
package-level templ function you call by name — `@driftwood.Card(p) { ... }` — with
immutable props structs (living in `driftwood`) carrying typed `datastar.Attrs`.
A wrong call is a compile error, not a registry miss. The framework's own error
rendering goes through `driftwood.ErrorPage`/`driftwood.ErrorAlert` (`render.go`).
`ui` itself keeps just two primitives, both `.templ`: `ui.Icon` and `ui.Defer`.

`ui.Icon("gear", ui.IconSize(...), ui.IconLabel(...))` emits
`<i class="icon icon-gear">`; the glyphs render through a Unicode `::before` map in
`input.css` — a deliberate stand-in until the planned build-time-subset icon font
ships (the font would contain only the glyphs the code references; `ui.UsedIcons()`
already tracks them).

## Tokens

Color comes from **`pkg/theme`**, which *derives* the whole vocabulary from a
preset of about a dozen numbers. Type and layout come from Tailwind v4 — one
generated `app.css`, built from `pkg/beach/view/css/input.css` (`make css`). The
kit emits semantic `dw-*` classes; the sheet styles them, so markup stays clean
and the whole kit restyles from one place.

**The palette is computed, not chosen.** Each token declares the backdrops it will
be seen against and the WCAG ratio it owes there, and the solver returns the color
that satisfies all of them with the most of its hue intact. That inverts how this
used to work: the previous palette was picked by hand against the same contrast
matrix and arrived at a muted `#3d7c82` accent, because by the time white label
text had its 4.5:1 and the focus ring had its 3:1, there was no color left to
spend. Contrast is now what *produces* the tokens rather than what they are graded
against, and re-theming the entire framework is one preset key.

| Group | Tokens |
| --- | --- |
| Surfaces | `--color-paper` (page) · `--color-panel` (cards/chrome) · `--color-panel-hover` |
| Ink | `--color-fg-strong` (headings) · `--color-fg-default` · `--color-fg-muted` · `--color-fg-disabled` |
| Edges | `--color-line-soft` (decorative) · `--color-line-strong` (component boundaries, 3:1) |
| Accent | `--color-accent` + `-hover`/`-text`/`-soft`, and `--color-on-accent` — the ink an accent fill carries, which is the paper color in both schemes |
| Categories | `--color-accent-2` / `--color-accent-3` — A/B/C and phase coding, picked for separation |
| Roles | `--color-good` / `--color-warn` / `--color-bad` / `--color-info` — buttons, badges, alerts, toasts and the form-error banner all tint from these, so overriding a role token repaints every role-colored component |
| Series | `--color-series-a…o` (15) at one shared lightness and one shared chroma fraction, so the ramp is balanced by construction; eight alternate `[data-chart-theme]` palettes redefine them per scope |
| Type | `--font-sans` / `--font-mono` (system-first stacks) |
| Spacing | `--space-2xs…3xl` and `--measure-text/narrow/default/wide` — see [16-components.md](16-components.md#spacing) |

Values are emitted as `oklch()`, not hex. A hex literal is six opaque digits;
`oklch(0.72 0.15 205)` states lightness, vividness and hue — the same terms the
theme was specified in. The engine is `pkg/color`, and OKLCH is what makes "as
vivid as this hue gets at this lightness" a question with an answer (`MaxChroma`).
Every chromatic token takes the same *percentage* of its own hue's maximum rather
than the same absolute chroma, because that maximum varies about threefold across
hues — one absolute value asks something easy of purple and something impossible
of cyan.

### Light and dark

Both schemes are derived, and light is **not an inversion**: it has its own ladder
(white cards raised off a soft ground, less tint, tighter value steps), because
flipping a dark ladder produces a photographic negative of a good light theme
rather than a good one.

The sheet answers all three states a visitor can be in:

```css
:root { … dark … }                                          /* the fallback */
@media (prefers-color-scheme: light) { :root:not([data-theme="dark"]) { … light … } }
:root[data-theme="light"] { … light … }
:root[data-theme="dark"]  { … dark  … }
```

Dark on bare `:root` keeps the kit dark-first and correct where the query is
unsupported; the query is what makes it automatic. **The `:not()` guard is the
part that gets forgotten** — without it an explicit choice is overridden by a
conflicting OS setting, and the toggle works in one direction and silently does
nothing in the other.

An explicit choice rides in [`prefs`](#) and `driftwood.Page` stamps `data-theme`
on `<html>` **during server render**. That is what makes a chosen theme survive
the first paint. The usual remedy — a blocking `<script>` in the head reading
`localStorage` — is a render-blocking script the [no-blocking law](#no-blocking)
rules out, and it flashes the wrong theme on every navigation when it fails.
`driftwood.SchemeToggle` is the control: three radios, because the choice has
three states and a two-way switch cannot express "let the system decide" — which
is the state a visitor starts in and needs a way back to.

### A theme at runtime

`app.css` carries every *rule*; `GET /_beach/theme.css` carries the ~40 *values*
those rules reference, with a strong ETag over their hash. That split is what the
token indirection was always for, and it means an app can be themed without
rebuilding the framework.

| Source | Wins when |
| --- | --- |
| `Config.Theme` | set — pins a theme in code |
| `Config.ThemeSource` | set and `Theme` is not — resolved at boot and on `App.ReloadTheme` |
| `view.ThemePreset` | neither is set — the preset the framework ships |

`ThemeSource` is a resolving *function*, not a table: the framework owns tables
for auth and sessions and nothing else, so an app backs its palette with a row, a
file or an environment variable, exactly as it already does for principals. The
theme is derived on change rather than per request — about 0.6ms, which is nothing
once and real money on every response — and swapped atomically, so a request
serves the whole old palette or the whole new one, never a mix.

`beach-palette -serve` is the explorer: a gallery of the shipped presets rendered
as real UI in both schemes, and an OKLCH hue wheel where the accent and the two
category colors are pins with harmony guides. It prints the Go literal for
whatever you land on, so what was tuned by eye is exactly what regenerates.

The Tailwind `@theme` block pins the `--radius-*` scale to `0px` — the sharp-corner
house law — so no component can round a corner without changing the law itself.

`.dw-root` carries `color-scheme: light dark` so native chrome — form controls,
the `<option>` popup, scrollbars — follows the palette rather than being pinned to
it, with the two `[data-theme]` rules pinning it when the visitor has chosen.
House rule: the kit writes semantic CSS (clean markup, styling lives in the
sheet), and `beach-vet` flags any hardcoded hex/OKLCH in templ or kit CSS —
color goes through a token, and spacing goes through the ladder. Type uses a system-first
stack so no font is fetched from a CDN; vendoring a specific webface (local
`@font-face` from `/static/fonts`) is a per-app opt-in.

The concrete inventory — every component, tiered by which example app proves it,
plus the **specimen** page (`ui/specimen`) that renders them all — is
[16-components.md](16-components.md). This doc is the mechanism; that one is the parts list.

## The laws

These are toolkit contracts, not advice. Every kit component and every skeleton
template is built to satisfy them, and they are measured rather than reviewed: the example
apps' perf gate for the first four, `beach-vet` and the kit's own tests for the fifth.

### No pop-in

The first paint is the final paint — for everything in the response. The server
renders final state, including signal initial values from cookies/session/DB; hidden
things ship hidden; no visible HTML is ever generated in client JS; theme classes
are on `<html>` before paint. Deferred sections (below) do not violate this law
because they reserve their exact dimensions up front: late content fills reserved
space, it never moves rendered pixels.

### No blocking

Nothing blocks first paint or the main thread. The stylesheet is the only
render-blocking resource, and it's immutable-cached so it costs one fetch per
deploy. Fonts are system-stack (no fetch at all); a vendored webface would use
`font-display: swap`. JS ships as deferred ES modules (`datastar.js` +
`chart.js`), so parsing never blocks rendering and a page is fully usable —
every CSS-native component works — before any script executes. SSE connects
after load; no synchronous XHR, no third-party scripts, no external CDNs.

### HTML and CSS first

Two scripts ship in the driftwood page head, both deferred modules: **Datastar**,
which earns its place only for what the platform genuinely can't do without script —
talking to the server (`@get`/`@post` fragments), signals shared across elements,
SSE patches — and **`chart.js`**, the chart interaction layer (tooltips, crosshairs,
the widget toolbar — [14-analytics.md](14-analytics.md#the-client-interaction-layer)),
which is pure progressive enhancement over server-rendered SVG: every chart renders
and updates without it. Everything else is HTML and CSS.

The platform does far more than it gets credit for: disclosure and accordions are
`<details>`/`<summary>`; modals are `<dialog>`; popovers, flyouts, and tooltips are the
`popover` attribute plus CSS anchor positioning; tabs, toggles, and menus open with
`:checked`/`:target`/`:focus-within` and native form controls. The kit builds every one
of these with **zero script**, so they work before any bundle loads, survive a script
error, and cost nothing on the main thread. Local presentational state — open/closed,
which tab, hovered — is never JavaScript. A component that reaches for script to do what
CSS already does is a defect.

This is what makes [no blocking](#no-blocking) hold so easily: most of a page is fully
interactive with no JS at all, and Datastar's bundle matters only the moment the user
does something that needs the server.

### The 14KB rule

A fresh TCP connection's initial congestion window is ~10 segments ≈ 14KB: a first
response that fits arrives in **one round trip**, before slow-start ever matters.
So `View.Page` targets **≤14KB compressed** — shell plus above-the-fold content,
server-rendered, complete. Everything heavier becomes a deferred section.

Enforcement is measurement, not vibes: in dev mode the framework logs every page
response's compressed size and warns over budget; the example apps' perf history
(JSONL, tracked in git) gates the budget in CI. The stylesheet doesn't count against
the 14KB (it's a separate cached request) — the budget is the HTML document.

### Accessible by construction

The fifth law. The target is **WCAG 2.1 Level AA**; the reasoning, the audit
that produced it, and the exceptions are [RFC 06](../rfc/06-accessibility.md).

1. **Every interactive element has an accessible name — and in the kit, that name is a
   catalog key.** A name a screen reader reads out is content: on a page rendered in
   Spanish, announcing "Close" is exactly as wrong as an untranslated heading. So the kit
   emits no literal `aria-label`; every one resolves through `i18n.T(ctx, "ui.a11y.…")`
   against the framework's embedded catalog, and `beach-vet`'s `a11y-literal-name` rule
   fires on a literal inside `pkg/ui` or `pkg/chart`. An app that configures no locales
   gets the English wording and pays nothing.
2. **Every control is associated with its label, its help, and its error.** `Field` does
   this itself: it publishes the ids of the text it rendered onto the context it hands its
   children, and the controls read them back into `aria-describedby` and `aria-invalid`.
   Nothing is wired at the call site. With no `For` to point at, `Field` becomes a
   `<fieldset>`/`<legend>` rather than emitting a label that names nothing.
3. **Every focusable element draws a visible ring at ≥3:1.** One rule in the a11y section
   of `input.css` covers the kit; the two controls whose real input is visually hidden
   (the switch, the tabs) have the ring relayed to their visible proxy. `--color-accent` is
   pinned to a lightness that clears 3:1 against paper, panel *and* panel-hover, so the
   indicator is visible wherever it is drawn.
4. **Color is never the only encoding, and the pairs are measured.** The long-standing
   half of this — a delta arrow beside a delta color, an icon beside an alert tint — is now
   joined by `contrast_test.go`, which parses the real tokens out of `input.css` and
   asserts every pair the kit paints against `rybitten.Contrast`: 4.5:1 for text (SC
   1.4.3), 3:1 for a component boundary or focus ring (SC 1.4.11). Two consequences for
   anyone editing the sheet: **readable text uses a token, never a raw `zinc-*` utility**,
   because a raw utility is outside what the test can see; and **`opacity` is not a
   de-emphasis tool**, because it silently divides whatever contrast the text had.
5. **No ARIA role without the states and children it implies.** An unnamed `role="img"`
   announces "image" and stops; a `role="tablist"` over things that are not tabs is worse
   for a screen reader than no role at all. Where the kit cannot honour a role it drops the
   role: `Tabs` is honestly a radio group (the ARIA tabs pattern needs roving tabindex, and
   [local interactivity is never script](#html-and-css-first)); an unnamed chart is
   `aria-hidden` inside a `<figure>` rather than a nameless graphic; `role="radiogroup"`
   and `role="group"` appear only when there is a name for them. The corollary for a
   *reactive* state: bind it with `ariaBoolExpr`, because Datastar writes a boolean-valued
   `data-attr` as an HTML boolean attribute, and a removed `aria-pressed` does not read as
   "not pressed" — it reads as "not a toggle button".
6. **Every layout reflows to 320px.** No horizontal page scrolling: rows of controls wrap,
   the two-column form stacks below `sm`, and a flex child holding an input carries
   `min-w-0` so it can shrink. A data table is the one exemption SC 1.4.10 grants, and it
   takes it inside its own `overflow-x` container — with a `Caption`, that container is
   also a named focusable region, so the scrolling is reachable by keyboard.
7. **Anything that moves, updates or expires can be stopped.** A live stream, an animation
   past five seconds, a notification on a timer: each is a thing the page does *to* the
   visitor, and SC 2.2.1 / 2.2.2 ask for a way out of it. The framework provides the
   mechanism rather than leaving it to each app — `driftwood.LiveToggle` pauses a stream
   and `adaptStream` honours the preference server-side even when no control is rendered,
   `prefs.AutoDismiss` turns off every toast timer, and `prefers-reduced-motion` drops the
   animations. The component's job is to honour those, never to invent its own.
8. **Anything reachable by hovering is reachable by the keyboard, and says the same
   thing.** SC 2.1.1 is about *all* functionality, which includes the tooltip holding the
   numbers. A highlight with no announcement is a keyboard path to nothing, so a chart
   figure that takes focus also carries a live region and speaks its server-rendered
   `data-tip` — the same text the pointer gets, because the keyboard drives the same code.

Two things follow from the framework's own architecture rather than from the components:

**The live region ships empty, before the message.** A region that arrives together with
its content is not announced (SC 4.1.3), so `Shell` renders `driftwood.LiveRegion` at
`beach.ToastTarget` on every page and toasts patch *into* it. `beach.Patch{Announce: "…"}`
is the general form — the way a server-driven change tells someone who cannot see it that
anything happened, with no client JavaScript involved.

**The document declares its language.** `<html lang>` and `dir` come from the request's
active i18n locale (`beach.Config.Locales`), not from a constant — a screen reader picks
its voice and pronunciation rules from that attribute (SC 3.1.1), so it has to follow the
content.

### Deferred sections

Anything bigger than the budget lazy-loads over Datastar. `ui.Defer` renders a
server-side placeholder with **exact reserved dimensions** (kit-styled skeleton,
zero layout shift) and a Datastar `@get` that fires on viewport intersection (or
load, for behind-a-tab content):

```templ
@ui.Defer(ui.DeferProps{
    ID:     "trade-history",
    Height: "24rem",                  // reserved space — late fill, no shift
    Get:    "/wallet/history",        // lands on a PageFunc; fragment patches in
})
```

The `@get` hits a normal `beach.PageFunc` — the framework's dual-purpose branch
returns the fragment, the patch morphs into the placeholder. Deferred sections live
below the fold or behind interaction; above-the-fold content is always in the first
response. One mechanism, three uses: 14KB overflow, expensive queries that shouldn't
block the first paint of cheap content, and behind-interaction panels.
